# Touch latency — implementation and original investigation

## Implemented in 0.9.3–0.9.5

- A 64-event timestamped queue retains down/move/up paths between render frames, coalesces identical stationary reports, preserves transitions preferentially under overflow and reports every overflow. Picking and physics replay the same contact record before the mesh deforms once.
- GPIO38 now wakes a dedicated priority-5 acquisition task. The ISR only records timing and notifies. Bounded fallback polling retains contact/release and sleep recovery; I²C reads use a 10 ms timeout instead of sharing the housekeeping loop. Physical interrupt timing is still unmeasured.
- A critically damped follower changes only the held local pull attachment. The native test measures 21 ms to 50% and 49 ms to 90%, versus 103/168 ms before. Bulk material, gravity, shake and release springs are unchanged. This is component response, not contact-to-photon latency.
- Native tests retain all 190 short-swipe phase cases, within-frame circles and repeated taps. USB-injected 20 ms swipes retain their path and release momentum. Neither substitutes for a real finger test.
- Diagnostics distinguish I²C errors from malformed reports, record GPIO level/interrupt age, queue age/overflow, task stack and recovery history. Observed quiet failures were `ESP_ERR_INVALID_STATE` from an unfinished I²C transaction, with no malformed coordinates. The FT3168 datasheet describes monitor-mode I²C nonresponse after shared-bus activity. The matching quiet/no-contact/high-INT condition now defers polling rather than repeatedly resetting; the inference is recorded, not presented as proven electrical diagnosis. Errors and deferrals remain visible.

Evidence: `tests/touch_history_check.cpp`, `tests/blob_physics_check.cpp`, `test-results/touch-response-0.9.3/native-checks.json`, its `visual-review/` sequences, and the later `test-results/lightweight-sleep-0.9.4/hardware-check.json`. The latter completed overlay sleep, injected touch/motion wake, audio resume and quiet monitoring with zero digitizer resets/overflows. Initial 0.9.3 acquisition-only runs that still reset the digitizer are preserved separately. Sustained physical use, actual IRQ wake and visible latency still need qualification.

## 0.9.17 polling correction — synthetic soak passed; physical qualification remains

A mixed-load run exposed a diagnostic coupling: the digitizer watchdog used the application's down state, so USB-injected dragging also accelerated polling of an untouched physical controller. It now uses the controller's own contact state; the reset path clears that state. Real GPIO38 acquisition and the 10 ms held-contact watchdog remain. No input queue, follower, bulk physics, renderer or display timing changed.

Fault reports now separate physical versus injected contact, IRQ pin level, mutex acquisition, bus-lock timeout and I²C transaction timeout. Errors still count normally, and recovery/quiet-deferral rules are unchanged. The two-direction injected-swipe and sleep/wake check passed, followed by 120 seconds of quiet/scan observations with no controller resets or queue overflows. The overall check retained 218 quiet-deferral sample failures and one raw transaction timeout. It does not prove physical wake or finger latency. The earlier 0.9.16 mixed run that failed on five non-deferred samples is preserved; a 90-second mixed preflight passed with all 62 failed samples classified quiet, and the fresh two-hour run passed with all 8,193 failed samples classified as quiet deferrals, 16,450 raw bus errors, zero non-deferred failures, decode errors, controller resets or queue overflows. No physical IRQ was generated by these injected tests.

## Original investigation (historical 0.9.0)

The following findings describe the implementation before those changes; they are retained as the measured baseline.

There are substantial software causes of the current input delay. Faster touch acquisition can help, but preserving gesture history and separating prompt finger attachment from the jelly body's slower response are likely the largest interaction improvements. This investigation did not modify or flash firmware. The recovered stable 0.9.0 implementation remains active.

## Measured on the device

A 22.00-second awake interval produced **57.41 successful register reads/s**, averaging **17.42 ms/read**, and **25.59 presented FPS**. Touch, display and audio error counters did not increase during that baseline. Successful register reads are not a measurement of unique controller reports or physical touch scan frequency.

Local USB touch commands were acknowledged in a median **1.89 ms** across 24 trials. This bypasses the capacitive controller. Repeated full-status polling noticeably slowed rendering and gave a median 76 ms until a touch was observed in physics. That intrusive figure must NOT be reported as physical input latency.

A second run used only one observation per contact, with randomized phase and five trials per delay:

| Wait after command acknowledgement (ms) | Contact already consumed by physics |
|---|---|
| 5 | 0/5 |
| 15 | 2/5 |
| 25 | 1/5 |
| 35 | 1/5 |
| 50 | 5/5 |
| 65 | 5/5 |
| 90 | 5/5 |

These are small-sample observations, not latency percentiles. USB/HTTP scheduling and snapshot acquisition add uncertainty. Under this contact workload, recent frame times were typically 46–56 ms; ordinary no-contact rendering was faster. All sampled contacts were consumed by the 50 ms observation. None of these tests measures when light actually changes on the panel.

## Three independent contributors

1. **Acquisition shares the housekeeping loop.** `main/services.cpp` calls `board_touch_tick()`, then motion sampling/retries and maintenance, then sleeps 16 ms awake or 32 ms asleep. Actual period therefore includes work time. Recovery or audio/power work can introduce longer gaps. Board-support source identifies touch interrupt GPIO38, but the active firmware does not configure it as an input interrupt. The TE interrupt on GPIO13 is separate and working.
2. **Only the latest touch is retained.** `input_touch()` overwrites one `Blob::Touch`. It preserves touchdown identity and position, but not the intermediate path. Physics runs once per rendered frame. A fast down/move/up sequence can finish before physics reads it: touchdown still creates the tap impulse, but the drag path and its directional forces can be lost. A source-driven native reproduction at a 38 ms frame interval found zero drag deformation for 19 of 38 relative phases of a 20 ms swipe and 9 of 38 phases of a 30 ms swipe. These are synthetic phase sweeps, not a measured miss rate for the user's fingers.
3. **The grabbed skin has a slow spring response.** With input available immediately and a high simulation rate, the current held-pull spring takes 39 ms to reach 10%, **103 ms to reach 50%**, and 168 ms to reach 90% of a step target. These measure the local pull spring, not the full silhouette or total contact-to-photon latency. This delay is additional to acquisition/render/presentation scheduling. It explains why simply polling faster would not make the skin feel attached to the finger.

Rendering also imposes a floor: 25.6 FPS is approximately 39 ms between completed frames, and actual interaction can cost more. The existing immutable frame buffer and TE-synchronized presenter intentionally prevent tearing. Its synchronization waits are not safe to delete simply to make latency counters smaller.

## Intermittent acquisition fault

The baseline and initial USB trial finished with zero touch errors. Later status checks found eight rejected reads and one controller reset, then sixteen rejected reads and two resets. The digitizer recovered and continued sampling in both observations. The existing recovery waits for eight consecutive failures and then toggles reset (20 ms low plus 50 ms startup delay). Such a recovery can cause a separate, occasional input gap. This investigation did not record the fault onset or establish whether the cause is electrical, report coherency, controller firmware or the driver. It must be instrumented separately rather than hidden by faster polling or blamed on CPU load. Final display/audio errors remained zero and rendering recovered to 26.47 FPS.

A separate 90-second direct-USB capture, including the normal transition to sleep, did not reproduce the fault: zero touch errors/resets, six successful single-read retries, and zero display/audio errors. Its logs are saved in `digitizer-health.json`. The intermittent fault remains unlocalized; the clean rerun does not disprove the earlier counters.

## Controller specification and limits

The [FocalTech FT3168 datasheet hosted by Waveshare](https://files.waveshare.com/wiki/common/DATA_SHEET_FT3168.pdf) specifies an **up-to-100 Hz report rate**, an INT signal when data is ready, and I2C up to 400 kbps. The firmware already uses 400 kHz I2C. A 100 Hz report rate corresponds to 10 ms report spacing; this is a published maximum, not a measurement of this unit's current configuration. Increasing host polling to 200 Hz would not prove 200 unique touch positions/s. Internal controller filtering and scan configuration remain unmeasured.

GPIO38 is confirmed in `../components/bsp/esp32_s3_touch_amoled_2_06/include/bsp/esp32_s3_touch_amoled_2_06.h` (`BSP_LCD_TOUCH_INT`). The live board's interrupt cadence, edge behavior, and timestamps still require instrumented physical swipes; the current firmware does not expose them.

## Recommended implementation order

1. **Preserve timestamped input history.** A bounded event buffer should retain down, move and up transitions independently of rendering. Process the captured path into physics before deforming/rendering once. Collapse duplicate stationary reports, never collapse an entire gesture into its final release. Include overflow diagnostics and an explicit release-safe overflow policy. Hit testing and physics should consume the same contact record; currently their separate snapshots can straddle a new touch.
2. **Make the local finger attachment responsive.** Use a strong local contact constraint or a faster held-only follower. Keep the bulk material, gravity response, release springs and traveling waves soft. The desired feel is promptly attached skin with a delayed wobbly body. A low-viscosity blob need not have a delayed grab point. Do not globally increase stiffness or reduce all damping.
3. **Read on controller interrupts.** Service GPIO38 promptly in a small task, with the ISR only waking that task; retain bounded fallback polling and existing fault recovery. Keep it independent of slow housekeeping work and retain low-duty sleep wake detection. Confirm actual report timing before attempting controller register tuning. Respect the current tight internal-memory budget.
4. **Then reduce presentation age.** Timestamp input acquisition, physics consumption, frame submission and completed transfer. Track gesture-age percentiles and missed transitions under real audio/Wi-Fi load. Use those measurements to optimize the stable renderer without reducing native image quality or removing TE synchronization. Faster 30 FPS rendering alone saves only about 6 ms of frame interval compared with this idle baseline.

## Acceptance criteria for a future fix

- An entire short swipe between two renders still applies directional drag/release momentum; rapid reversals and circles retain their trajectory.
- Measure physical interrupt-to-read timing; do not substitute USB acknowledgement for digitizer latency.
- Finger attachment responds on the first frame that consumes the event, while the body retains its accepted jelly behavior and release wobble.
- No changes to shader, resolution or tearing protection; no new resets, display/audio faults, stuck contacts or sleep/wake regressions.
- Confirm fingertip-to-visible-motion latency with high-speed camera footage if a precise end-to-end number is required. A framebuffer screenshot and USB status cannot establish it.
